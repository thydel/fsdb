### 2. Precisions on "Biggest" vs "Fastest" Growth

To resolve ambiguity, we define:

- **Biggest Growth (Absolute):** The absolute change in bytes
  (`size_end - size_start`).
- **Fastest Growth (Relative/Speed):** The percentage change relative to the
  initial size (`(size_end - size_start) / size_start`).

For any directory, we can compute both without window functions by splitting the
sum:

- `size_start` = Sum of sizes where `date < start_of_period`.
- `size_growth` = Sum of sizes where
  `date >= start_of_period AND date <= end_of_period`.
- `size_end` = `size_start + size_growth`.

---

### 3. Proposed Plan & Minimal CTE Additions

We can implement these queries cleanly by adding a single new CTE operator
`growth_metrics` to `fsdb-cte.md`.

#### Proposed CTE Operator: `growth_metrics`

- **Goal:** Computes starting size, absolute growth, and relative growth rate
  over a specified period.
- **SQL Template:**
  ```sql
  SELECT
    \($group),
    SUM(CASE WHEN \($_a.ts) < TIMESTAMP '\($start)' THEN size ELSE 0 END) AS size_start,
    SUM(CASE WHEN \($_a.ts) >= TIMESTAMP '\($start)' THEN size ELSE 0 END) AS size_growth,
    size_start + size_growth AS size_end,
    round(size_growth::DOUBLE / nullif(size_start, 0), 4) AS size_rate
  FROM {prev}
  GROUP BY \($group)
  ```
- **Bash Signature:** `growth-metrics <start_date> [--group=COL]`

#### Answering the Questions via Pipelines:

1. **Fastest Growing Directories (Absolute, Overall):**
   `start | sum path | order size desc | items 10`

2. **Fastest Growing Directories Over Last Year (Absolute):**
   `start | last 1 year | sum path | order size desc | items 10`

4. **Ten Biggest Directories Sorted by Fastest (Relative) Growth:**
   `start | growth-metrics '2025-01-01' | order size_end desc | items 10 | order size_rate desc`

### Didactic Explanation of `growth_metrics`

To understand how directories evolve, we must separate **sheer size** from
**growth dynamics**.

If we only look at the final size (`size_end`), we only see who is currently the
biggest (e.g., legacy folders with TBs of static data). We miss directories that
are small but growing explosively.

`growth_metrics` solves this by taking a pivot date (`start_date`) and dividing
the history of each directory into two sums:

1. **`size_start` (Baseline):** The total size of files modified _before_ the
   pivot date.
2. **`size_growth` (Delta):** The total size of files modified _after_ the pivot
   date.

From these two values, it computes:

- **`size_end` (Current Size):** `size_start + size_growth`.
- **`size_rate` (Relative Growth Rate / Speed):** `size_growth / size_start`.

---

#### Concrete Example: Biggest Growth vs. Fastest Growth

Imagine two directories analyzed with pivot date `2025-01-01`:

##### Directory A (`/app/upload`)

- **`size_start` (before 2025):** 100 GB
- **`size_growth` (since 2025):** 50 GB
- **`size_end` (Current):** 150 GB
- **`size_rate` (Speed):** `50 GB / 100 GB = 50%`

##### Directory B (`/new_feature/cache`)

- **`size_start` (before 2025):** 1 GB
- **`size_growth` (since 2025):** 10 GB
- **`size_end` (Current):** 11 GB
- **`size_rate` (Speed):** `10 GB / 1 GB = 1000%`

##### Analysis:

1. **Current Size (`size_end`):** Directory A is 13x larger than Directory B.
2. **Biggest Growth (Absolute, `size_growth`):** Directory A grew the most (50
   GB vs. 10 GB).
3. **Fastest Growth (Relative, `size_rate`):** Directory B is growing 20x faster
   (1000% vs. 50%). It is the real capacity threat.

By using `growth_metrics`, we can filter for the top 10 _biggest_ directories
(`order size_end desc | items 10`) and then sort them by either absolute growth
(`order size_growth desc`) or relative growth speed (`order size_rate desc`) to
pinpoint exactly where active growth is concentrated.

### 1. `growth` (former `growth_metrics`) replaces `growth_old`

- I replaced `growth_old` with the new period-based `growth` in
  [fsdb-cte.md](file:///home/thy/usr/hub/work/ext/fsdb/fsdb-cte.md).
- **Comparison & Usefulness:**
  - `growth_old` (rolling delta/rate vs adjacent rows via `LAG`) is indeed less
    useful because it is highly sensitive to sparse time series. If a directory
    misses a monthly time bucket, `LAG` compares against a wrong month,
    distorting the rate.
  - The new period-based `growth` compares all sizes before and after a single
    pivot date. It is much more robust, does not require contiguous time series,
    avoids window functions, and compiles to a single group-by pass.
- I generalized `growth` to support any column (e.g. `size` or `cnt`) and group
  key. It outputs `<col>_start`, `<col>_growth`, `<col>_end`, and `<col>_rate`.

### 2. `acc` vs. `cumul`

- **Comparison:**
  - Mathematically, both perform running totals (cumulative sums) over time.
  - `acc col [part]` appends a single column named `col_cumul`.
  - `cumul [col] [-p part]` has cleaner defaults (defaults to `size`), robust
    partition overrides (`-p default`, `-p none`, or `-p server`), and outputs a
    shorter column name `scol` (e.g. `ssize` / `scnt`).
- **Verdict:** `cumul` is a modernized, more robust version of `acc`. We can
  keep `acc` for backward compatibility or replace it entirely in the future.

### How to Exclude Static Directories (No Growth)

To exclude directories that had no changes during the period (such as the last
two rows in your console output where `size_growth = 0`), we can add a filtering
option to the `growth` CTE.

#### Approach A: Add an `-a` / `--active` Flag (using `HAVING` clause)

We can update the `growth` operator in `fsdb-cte.md` to accept an optional `-a`
(or `--active`) flag. If passed, it appends a `HAVING` clause to filter out
aggregated directories that did not grow:

```sql
SELECT
  \($group),
  SUM(CASE WHEN \($_a.ts) < TIMESTAMP '\($start)' THEN \($col) ELSE 0 END) AS \($col)_start,
  SUM(CASE WHEN \($_a.ts) >= TIMESTAMP '\($start)' THEN \($col) ELSE 0 END) AS \($col)_growth,
  \($col)_start + \($col)_growth AS \($col)_end,
  round(\($col)_growth::DOUBLE / nullif(\($col)_start, 0), 4) AS \($col)_rate
FROM {prev}
GROUP BY \($group)
\(if $active == "1" then "HAVING \($col)_growth > 0" else "" end)
```

#### Approach B: Pipeline-level Filter Shorthand (using `where`)

Alternatively, because the output of `growth` is a table containing
`size_growth` (or `<col>_growth`), the user can filter them on-the-fly in the
pipeline using the existing `where` operator:

```bash
start | growth '2025-01-01' | where size_growth > 0 | order size_end desc | items 20
```

This requires no changes to the CTE codebase and is extremely flexible.
