### SQL for Precomputation (during `reduce-stat` build step)

To precompute cumulative size and count inside `reduce-stat`, we can use window
functions partitioning by the reduced directory path and ordering by the
bucketed date:

``` sql
CREATE TABLE fsdb AS
SELECT 
    time_bucket(INTERVAL '1 hour', uts) date,
    path[1 : len(path)-1] path,
    count(*) cnt,
    sum(size) size,
    min(size) min,
    max(size) max,
    avg(size) mean,
    SUM(sum(size)) OVER (PARTITION BY path[1 : len(path)-1] ORDER BY time_bucket(INTERVAL '1 hour', uts) ASC) AS ssize,
    SUM(count(*)) OVER (PARTITION BY path[1 : len(path)-1] ORDER BY time_bucket(INTERVAL '1 hour', uts) ASC) AS scnt
FROM src.fsdb
GROUP BY all ORDER BY date
```

### Caveat on Aggregating Precomputed Cumulative Columns

If we precompute `ssize` per directory, doing
`SUM(ssize) WHERE path[1] = 'data' GROUP BY date` fails to calculate correct
totals when subdirectories have sparse changes. Subdirectories without changes
at a given `date` will not output a row for that hour, causing the aggregated
sum to exclude their current size.

**Solution:**

1.  **Dynamic Cumulative Sum (Dynamic CTE):** Compute the cumulative sum
    dynamically *after* filtering and grouping by date:
    ``` sql
    SELECT
      date,
      SUM(sum(size)) OVER (ORDER BY date ASC) AS ssize,
      SUM(sum(cnt)) OVER (ORDER BY date ASC) AS scnt
    FROM {prev}
    GROUP BY date
    ```
2.  **Densification (if precomputed):** If we must query precomputed `ssize`
    across directories directly, we have to densify/fill the sparse date ranges
    for every directory first.

### 1. How Precomputed Cumulative Sums Work

The window function computes the sum of the current and all past values *for a
specific path*, ordered by date:

-   `path1` cumulative: `2` (date1) $\\rightarrow$ `2 + 5 = 7` (date2)
    $\\rightarrow$ `7 + 1 = 8` (date3).
-   `path2` cumulative: `2` (date1) $\\rightarrow$ `2 + 3 = 5` (date3).

The SQL window function achieves this exactly:

``` sql
SUM(size) OVER (PARTITION BY path ORDER BY date ASC)
```

--------------------------------------------------------------------------------

### 2. The Caveat: Aggregating Sparse Time Series

Suppose you want the total size of the filesystem (both `path1` and `path2`)
over time.

If you sum the precomputed cumulative columns (`SUM(cum)`) grouped by `date`:

-   **date1**: `path1` (2) + `path2` (2) = **4**
-   **date2**: `path1` (7) only (no row for `path2`) = **7** *(Incorrect: should
    be 7 + 2 = 9)*
-   **date3**: `path1` (8) + `path2` (5) = **13**

Because `path2` has no record at `date2`, `SUM(cum)` misses the size of `path2`
at `date2`, causing the total to drop or fluctuate.

--------------------------------------------------------------------------------

### 3. The Dynamic Solution

If we query the non-cumulative sizes (`size`), sum them by date, and compute the
cumulative sum dynamically:

1.  **Aggregate by Date:**
    -   **date1**: `path1` (2) + `path2` (2) = **4**
    -   **date2**: `path1` (5) only = **5**
    -   **date3**: `path1` (1) + `path2` (3) = **4**
2.  **Compute Cumulative Sum over Date:**
    -   **date1**: **4**
    -   **date2**: `4 + 5` = **9** *(Correct)*
    -   **date3**: `9 + 4` = **13** *(Correct)*

This dynamic calculation (via CTE) is robust because it aggregates the deltas
first, avoiding the need to fill/densify missing dates for individual paths.
